# 16 — Architecture & FAQ

Sources: https://docs.levimc.org/LeviLamina/developer_guides/architecture/ + https://docs.levimc.org/LeviLamina/developer_guides/faq/ (canonical: `docs/main/contents/developer_guides/{architecture,faq}.md`).

## Layered architecture

```
Mod Code (User)
   │ uses
ll/api  (Public API — stable, semver-guaranteed, LLAPI/LLNDAPI exports, ~255 headers)
   │ implements
ll/core (Internal — ModRegistrar, NativeModManager, CrashLogger, built-in commands /version /ll /tpdim /crash, tweaks)
   │ uses
mc/     (Bedrock engine headers — reverse-engineered, READ-ONLY, generated by header_generator)
```

- **Mod code only touches `ll/api/`**. Key namespaces: `ll/{base,command,event,form,mod,service,...}`; `mc/` exposes `::Actor`, `::Player`, `::Mob`, `::Level`, `::Dimension`, `::BlockSource`, `::ServerInstance`, `::Minecraft`, `::CommandRegistry`, `::Packet`, `::NetworkIdentifier`, ...
- `src/` = common + server; `src-server/` = server-only extensions; `src-client/` = client-only (input, render/client events, `KeyRegistry`).
- Design principles: type-safe (C++20 concepts), `Expected<T>` error handling, async via coroutines + executors, compile-time reflection for serialization, event-driven pub/sub.
- Patterns: Singleton (`EventBus`, `CommandRegistrar`, `ServiceManager`, `ModManagerRegistry`), Factory (`PacketRegistrar`, emitters), Observer (EventBus/Listener/Event), DI (ServiceManager).
- Memory: mimalloc default allocator; `shared_ptr`/`unique_ptr` ownership; `optional_ref` for non-owning Bedrock references; `HookRegistrar` for hook lifetimes.
- Threading: **server thread** (main game loop, single-threaded — where all game-state MCAPI belongs), thread pool (background), network threads; sync via executors, atomics, mutexes.

## Server vs client builds (`--target_type`)

| Aspect | Server | Client |
|---|---|---|
| Sources | `src/` + `src-server/` | `src/` + `src-client/` |
| MC headers | `bedrockdata:server` | `bedrockdata:client` |
| API surface | Common + Server | Common + Client |

API availability: Base/Command/Event(player,world)/Form/Service = **both**; Event(server) = server-only; Event(client/input/render) + Input = client-only. Runtime: server loaded by PreLoader into `bedrock_server_mod.exe` (produced from `bedrock_server.exe` by PeEditor; original kept as `.bak`); client into `Minecraft.Windows.exe` (patched in place).

## FAQ (verbatim digest)

**Q: Difference between server and client commands?**
Server commands are registered by the server, executable by the server and all connected players. Client commands are handled entirely by the client that registered them — other players and the server never see them. On BDS, mods can only register server commands; in a local world (client hosting an internal BDS) both; in multiplayer client mode only client commands. Instances: `CommandRegistrar::getInstance(false)` (server) / `getInstance(true)` (client).

**Q: Commands registered in `enable()` work on the server (BDS) but fail on the client?**
The timing of "mods enabled" differs: the server enables mods after server initialization (world loaded); the client enables them after the game startup completes (main menu). So at client `enable()` time no command registration can succeed — client or server sided. Fix: register in `ServerCommandRegisterEvent` (server commands) / `ClientCommandRegisterEvent` (client commands).

**Q: ACCESS_VIOLATION when a mod calls MCAPI (e.g. `Player::disconnect()`)?**
Check whether the calling code runs on the `MC_SERVER` thread. Most server-side MCAPIs can only be called from the `MC_SERVER` thread — a Minecraft game-design limitation. See `docs/10-coroutines-threads-chrono.md` for executors.
